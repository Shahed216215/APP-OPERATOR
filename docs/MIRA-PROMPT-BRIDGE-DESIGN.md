# Mira ↔ APP-OPERATOR ↔ ChatGPT Prompt Bridge
## Future implementation design — NOT IMPLEMENTED

**Status:** Design reserved for a later implementation phase  
**Repository:** APP-OPERATOR  
**Scope:** Android Operator handoff to the official ChatGPT Android app and return of the response to Mira  
**Current release boundary:** This document does not authorize implementation in the current Claude launcher / app-discovery phase.

---

## 1. Intended workflow

1. Mira creates a bounded work prompt and submits a job to the Operator bridge queue.
2. APP-OPERATOR receives the job from the paired Mira backend.
3. If the bridge's persistent **ALLOW** grant is ON, the Operator opens the official ChatGPT Android app and submits the prompt using only supported, explicitly scoped UI actions.
4. The Operator waits for the assistant response to complete.
5. It captures the response when the accessibility tree exposes reliable text. If not, it reports that automatic capture is unavailable and offers a manual copy/paste fallback.
6. The Operator returns the response and job receipt to Mira.
7. The cycle repeats while ALLOW remains ON.

The user must not be asked to approve every routine prompt or response transfer after enabling ALLOW.

## 2. Persistent ALLOW / OFF grant

ALLOW is a standing, revocable permission for this one integration. It is not blanket Android accessibility authority.

When ALLOW is ON:
- Permit routine prompt fetch, ChatGPT handoff, response capture, and return to the paired Mira backend.
- Do not show a per-job approval dialog for these routine actions.
- Display a persistent, obvious ALLOW state and a one-tap OFF/revoke control.
- Show the grant scope, paired backend identity, last activity, and recent job status.

When ALLOW is switched OFF:
- Stop polling and claiming new jobs.
- Stop any new ChatGPT UI actions immediately.
- Do not upload a response after revocation.
- Mark an in-flight job CANCELLED if safely stopped; otherwise INCONCLUSIVE.
- Require the user to turn ALLOW ON again before resuming.

The grant must be invalidated on device unpair, token revocation, app data reset, or security integrity failure.

## 3. Strict permission boundary

The grant covers only:
- The paired Mira bridge service.
- The configured official ChatGPT package: `com.openai.chatgpt`.
- Routine prompt submission and response retrieval for queued Mira jobs.

It does not cover:
- Passwords, OTPs, authentication codes, or credential extraction.
- Payments, purchases, money transfers, or financial commitments.
- Account settings, security settings, account creation, or account deletion.
- Deleting user data, sending messages to unrelated recipients, or external legal commitments.
- Arbitrary apps, arbitrary taps, unrestricted gestures, or general-purpose device control.
- Changes to Operator permissions or the ALLOW grant itself initiated by prompt content.

A prompt, webpage, or ChatGPT response is untrusted data. It cannot expand the grant, change the allowlist, or override Operator policy.

## 4. Pairing and backend contract

- Pair using a short-lived, single-use pairing code or QR code generated by an authenticated Mira administrator.
- Redeem the code once; issue a device-scoped, revocable token with bridge-only permissions.
- Never store or transmit the Mira Admin bearer token on Android.
- Store the device token using Android Keystore-backed encryption.
- Require HTTPS; reject cleartext transport and invalid certificates.
- Bind every job to a device ID, job ID, creation time, expiry, and idempotency key.
- Apply request/response size limits, rate limits, bounded retries, and claim leases.
- Keep audit metadata without writing secrets or full prompt/response bodies to diagnostic logs.

Suggested lifecycle:

`QUEUED → CLAIMED → SENT_TO_CHATGPT → RESPONSE_CAPTURED → RETURNED`

Terminal or exceptional states:

`FAILED | INCONCLUSIVE | CANCELLED | EXPIRED`

Suggested bridge endpoints (final paths and schemas must be reviewed against the Mira backend before implementation):

- Pair / redeem one-time code.
- Read current grant and device status.
- Fetch and claim the next eligible job.
- Report handoff and capture state.
- Return response with job ID, device ID, timestamp, capture method, and content digest.
- Revoke device or bridge grant.

All endpoints must use a dedicated bridge authentication scope. Android must never call Mira's administrative task-execution endpoint.

## 5. Android implementation boundary

- Keep the existing Evolution 20 UI and emergency-stop behavior intact.
- Add a dedicated Prompt Bridge settings/control card; do not repurpose the global emergency stop.
- Use a visible persistent ALLOW / OFF switch with immediate revocation.
- Restrict accessibility event handling and actions to the ChatGPT package for this feature.
- Do not inspect password or editable credential fields.
- Use only known, validated ChatGPT input and send controls; do not perform arbitrary coordinate tapping.
- Treat accessibility text as incomplete until a stable completion condition is observed.
- If ChatGPT changes its UI or hides response text, report INCONCLUSIVE and use the manual fallback.
- Run bridge polling only under a clearly disclosed lifecycle policy; background execution requires a separately reviewed foreground-service design and notification.

## 6. Reliability, privacy, and audit

- Use bounded exponential backoff and idempotent job handling.
- Never silently resend a prompt after an uncertain send result.
- Never claim a response was returned until Mira acknowledges the matching job ID.
- Do not log prompt bodies, response bodies, credentials, or device tokens.
- Provide a local activity receipt with timestamps, job ID, status, and capture method.
- On network loss, ChatGPT app failure, timeout, or ambiguous UI state, use FAILED or INCONCLUSIVE rather than PASS.
- OFF must take priority over retries and queued work.

## 7. Required tests before implementation can be accepted

Backend:
- One-time pairing code expiry and replay rejection.
- Device-scoped authorization and denial of admin routes.
- Queue claim lease, expiry, idempotency, and duplicate response rejection.
- Device revoke and ALLOW OFF enforcement.
- Payload size limits, rate limits, and audit metadata redaction.

Android:
- ALLOW persistence across process restart.
- Immediate OFF behavior and no post-revocation upload.
- Allowlist enforcement for ChatGPT only.
- Keystore token storage and invalid-token handling.
- Queue parsing, retries, duplicate suppression, and job expiry.
- Response completion detection, inaccessible-response fallback, and truthful INCONCLUSIVE state.

End-to-end:
- Physical-device pairing.
- ALLOW ON → Mira job → ChatGPT prompt → completed response → Mira acknowledgement.
- ALLOW OFF during queued, claimed, sending, and capturing states.
- App restart, network loss, ChatGPT UI variation, and backend revoke.

A CI build or JVM unit-test pass is not proof of physical-device accessibility behavior. End-to-end acceptance requires a real Android device test.
